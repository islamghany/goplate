# ADR-0011: Observability with OpenTelemetry, Prometheus exposition and `slog`

- **Status:** Accepted
- **Date:** 2026-10-24
- **Deciders:** Islam Mostafa
- **Tags:** ops, observability

## Context

JSON logs with a per-request trace ID are a good start, but two things
usually go wrong. The ID is generated by the server even when the request
already carries a `traceparent` or `X-Request-ID`, so it can't connect to
upstream traces. And logging goes through a custom wrapper around `slog`
with a non-standard API, so libraries that expect `*slog.Logger` can't use
it. Metrics are often missing altogether.

## Decision drivers

1. Vendor neutrality: switching between Jaeger, Tempo, Datadog or Honeycomb
   should be a config change.
2. Logs, traces and metrics should be correlated (same trace ID everywhere).
3. Zero cost when disabled; nothing extra needed to run locally.
4. Standard APIs, so third-party libraries (pgx, River, go-redis) can plug in.

## Considered options

1. **OpenTelemetry** for traces and metrics, a **Prometheus** `/metrics`
   endpoint through the OTel exporter, and **`log/slog`** with a
   trace-aware handler.
2. **Vendor SDK** (Datadog, New Relic) used directly.
3. **Prometheus `client_golang` only**, with no tracing.
4. **Logs only**.

| Option               | ✅                                                          | ❌                                                   |
| -------------------- | ---------------------------------------------------------- | ---------------------------------------------------- |
| OTel + Prom + slog   | Vendor-neutral standard; instrumentation for `net/http`, pgx, go-redis, River; one API for traces and metrics | The OTel SDK setup is verbose; the metrics API is lower-level than `client_golang` |
| Vendor SDK           | Polished, all in one                                       | Lock-in; changing vendors means touching every file  |
| Prometheus only      | Simple, widely used                                        | No distributed traces; you can't see *where* latency comes from |
| Logs only            | Minimal                                                    | Can't answer "p99 latency by route" or "why is this request slow" |

## Decision

We use **option 1**.

**Tracing**

- An OTel `TracerProvider` with an OTLP exporter (gRPC or HTTP, set by the
  standard `OTEL_EXPORTER_OTLP_*` environment variables). With
  `OTEL_SDK_DISABLED=true`, a no-op provider is used.
- W3C `traceparent` and `baggage` propagation. Incoming traces are
  continued, not restarted.
- Instrumentation: `otelhttp` on the router, plus the pgx tracer, go-redis
  hooks and River middleware, so a span tree goes from the HTTP request
  through SQL to the job.

**Metrics**

- The OTel `MeterProvider` with the Prometheus exporter, served at
  `/metrics` on a **separate internal admin port** (`ADMIN_ADDR`, default
  `:9090`), never on the public port.
- Built in:
  - HTTP RED metrics (rate, errors, duration) labeled by **route pattern**,
    never the raw path, to avoid label explosion
  - pgxpool statistics
  - Go runtime metrics
  - cache hits and misses
  - rate-limit rejections
  - job outcomes
- The admin port also serves `net/http/pprof` when `ADMIN_PPROF=true`.

**Logging**

- Plain `*slog.Logger` everywhere. **We don't wrap it in a custom logger
  type.**
- A custom `slog.Handler` adds `trace_id`, `span_id` and `request_id` from
  `ctx`, so you must log with the `...Context` methods
  (`log.InfoContext(ctx, ...)`). A linter rule (`sloglint`) enforces this.
- JSON output in production, text in development (`LOG_FORMAT`).
- **Request ID**: an incoming `X-Request-ID` is accepted if it's a short,
  safe value; otherwise one is generated. It's echoed back in the response
  and included in every error body (ADR-0018).
- **Secrets**: config secrets use a type whose `LogValue()` redacts the value
  (ADR-0016). Request bodies are never logged.

## Consequences

### Positive

- One trace ID connects logs, spans and error reports.
- Changing the backend is a matter of environment variables.

### Negative / trade-offs we accept

- More setup code in `internal/platform/otel`. It's written once and
  documented.
- Developers must use `InfoContext` and friends; the linter catches misses.

## Revisit if

- The OTel logs bridge becomes the norm in your stack. Then send logs
  through OTLP too and drop stdout scraping.
